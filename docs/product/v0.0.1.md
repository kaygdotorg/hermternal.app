# Hermternal v0.0.1 product specification

Status: normative planning specification.

This document defines the v0.0.1 product boundary. It applies to the web, iOS, iPadOS, and macOS clients and to the disposable proofs that support them. This repository is still in the planning and high-fidelity prototype phase. These documents and proofs are not production credentials, production configuration, or a live Hermes integration.

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative.

## Product purpose

Hermternal is a live chat client for Hermes Agent through the Hermes Dashboard protocol. A user can sign in, connect to one configured Hermes server, create or restore a chat session, send prompts, follow streamed work, and recover from normal connection failures.

Hermes remains the source of truth for the transcript and session state. Hermternal is a client. It does not become a dashboard administrator, a filesystem browser, an SSH client, or a second Hermes backend.

## In scope

### Supported client targets

- **Web** is a static TypeScript and Svelte client. It runs from the public HTTPS origin beside the Dashboard.
- **iOS and iPadOS** are native SwiftUI clients. They use platform authentication sessions, URL loading, secure storage, lifecycle handling, accessibility, and window or scene restoration.
- **macOS** is a native SwiftUI client. Its implementation may proceed after the shared Apple contract, authentication, and interaction layers are stable. It uses native windows, menus, keyboard commands, focus, accessibility, and deep links.

The web and Apple implementations MUST share protocol contracts, redacted fixtures, state definitions, test scenarios, and semantic design-token names. They MUST NOT share UI, networking, authentication, persistence, lifecycle, or accessibility implementations.

### User workflows

The v0.0.1 client MUST support these workflows:

1. Discover the authentication providers exposed by the target Dashboard.
2. Complete an approved browser or native sign-in flow.
3. Establish an authenticated Dashboard connection.
4. Create a session and restore the last known session.
5. Submit prompts and render the server stream.
6. Render tool activity, approval requests, clarification, interruption, success, and failure states.
7. Reconnect after a recoverable disconnect without creating a duplicate session.
8. Change the active model. An idle session applies the change immediately. A streaming session may defer a normal change to the next turn. If the deferred choice needs expensive-model confirmation, the pinned server drops it; the client must ask for confirmation and submit the choice after the current turn.
9. Open a session from a canonical deep link and restore the requested message when it exists.
10. On web only, open Terminal mode through the approved `/api/pty` contract. Terminal mode renders the Hermes TUI, accepts interactive input, and supports Hermes reattachment for up to 30 minutes after navigation or disconnect. At the pinned revision, **Close** detaches the client and stops retries; it does not explicitly kill the PTY process.

The web and Apple clients MUST expose clear loading, empty, focused, disabled, success, failure, reconnecting, and expired-session states where the workflow can reach them. The web client MUST support keyboard and browser zoom. Apple clients MUST support VoiceOver, Dynamic Type, Switch Control, and reduced motion.

### Navigation and persistence

Deep links are a first-class navigation feature. The canonical grammar and resolver rules are defined in [`docs/architecture/deep-links.md`](../architecture/deep-links.md). The grammar is independent of product and Hermes protocol versions.

The client MAY persist server settings, drafts, the last session, and lightweight UI preferences. It MUST NOT maintain a local transcript mirror in v0.0.1. It MUST resolve transcript content from Hermes after authentication.

One configured Hermes profile is supported per server connection. Profile aggregation and profile switching are out of scope. User-facing sharing of session links is deferred to v0.0.2, although internal restoration, Spotlight, and window or scene links are in scope.

### Compatibility and proof

Each implementation MUST use the frozen Hermes Dashboard contract, redacted fixtures, and parity scenarios. The release MUST pin an immutable Hermes source commit SHA. Because the pinned Dashboard does not expose that SHA or a stable wire-version field, the deployment MUST provide reviewed out-of-band attestation and the proof MUST run a non-destructive behavioral probe. Missing, mismatched, or untested evidence blocks protocol use. Exact route names, methods, message forms, and fixture ownership belong to [`contracts/hermes-dashboard/manifest.md`](../../contracts/hermes-dashboard/manifest.md), not to this product summary.

The deployment proof MUST cover both Caddy and Traefik. It MUST prove same-origin HTTPS routing, authentication, cookie handling, WebSocket upgrades, the web-only `/api/pty` path, default denial, private binding, firewall rules, and log redaction. The full matrix is in [`docs/deployment/proof-matrix.md`](../deployment/proof-matrix.md).

## Out of scope

The following are not v0.0.1 product features or client transports:

- Android and Windows clients.
- Dashboard administration or dashboard configuration UI.
- Direct SSH access.
- Direct use of the separate Hermes API-server contract.
- Direct access to, browsing of, or publication of `~/.hermes`.
- Hermes terminal-backend selection outside the approved web-only Terminal mode contract.
- More than one configured profile per server connection, profile aggregation, or profile switching.
- A local transcript database or transcript mirror.
- User-facing session-link sharing before v0.0.2.
- Production telemetry, release signing, app-store work, deployment automation, or live user data.
- A Hermternal-owned authentication provider, provider ordering, or provider policy.
- Native OAuth or OIDC providers whose reviewed callback transport is not accepted by the pinned Hermes native route or is not proven on the target Apple platform. No upstream change is approved for v0.0.1. The native username/password provider cookie path remains supported when discovery advertises it.
- Storing passwords, reusable Hermes credentials, access tokens, or WebSocket tickets in browser storage or source control.

The product may use disposable local fixtures and mock servers to prove behavior. A proof is not permission to add a production secret, a provider credential, or a deployable production file.

## Release gates

A v0.0.1 implementation is not ready until all of these conditions hold:

- The supported route and message surface is recorded in `contracts/hermes-dashboard/manifest.md`.
- The compatibility record contains a full pinned Hermes source SHA and redacted evidence for that revision. The source-only planning portion is reproducibly checked by [`planning_review.json`](../../contracts/fixtures/source-audit/planning-reconciliation/planning_review.json) and its local [`validate.py`](../../contracts/fixtures/source-audit/planning-reconciliation/validate.py) validator.
- Missing or mismatched deployment attestation, or a failed behavioral probe, blocks protocol use. The client does not guess, downgrade, or silently use another route shape.
- Browser and Apple authentication behavior passes the provider-neutral matrix. The native password-provider path uses an isolated server-issued cookie session; the pinned `basic` provider is implemented by `BasicAuthProvider`. A provider that requires unsupported native OAuth or OIDC callback transport is not presented as supported.
- Caddy and Traefik pass the same deployment proof cases and produce equivalent allow or deny results.
- Web and Apple clients pass the same contract, fixture, state, deep-link, and recovery scenarios while keeping platform-native implementations.
- Keyboard access, screen-reader labels, Dynamic Type or browser zoom, reduced motion, loading, empty, success, and failure states are verified for each shipped workflow.
- Performance checks report measured startup, input, stream-render, reconnect, memory, and bundle behavior. The project does not use unsupported performance claims.

This file is a specification and a planning boundary. It does not authorize a live integration or a production deployment.
