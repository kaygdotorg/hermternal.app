# Browser authentication boundary

`browser-auth.ts` implements the reviewed browser-cookie operations for W-04:

- `POST /auth/password-login` with the selected password provider;
- `GET /api/auth/me` as the required identity-verification barrier; and
- `POST /auth/logout`, followed by `GET /api/auth/me` to prove the server session is gone.

The implementation uses relative same-origin paths, `credentials: same-origin`, no-store requests, bounded response bodies, fatal UTF-8 decoding, duplicate-key-rejecting JSON, fixed diagnostics, and explicit cancellation. Password login rejects duplicate actions. The password response deadline remains active through bounded body consumption; caller cancellation or timeout cancels the reader before the transient normalized input can remain in an open read. Provider discovery applies the same cancellation rule to streamed and no-body synthetic responses. A same-generation `ProviderDiscoveryError('aborted')` is treated as cancellation, while other provider failure codes remain visible as bounded provider-unavailable state. Logout coalesces duplicate actions and treats the identity probe as the authority only for genuinely ambiguous network or timeout outcomes.

A password exists only in the transient request input and JSON request body. The boundary does not place passwords, cookies, refresh material, provider response details, or identity tokens in storage, URLs, errors, diagnostics, fixtures, or retained output. Hermes owns the protected session cookies. The browser never reads their values.

Password login success is not enough to enable chat. The exact `GET /api/auth/me` response must pass the strict REST identity projection first, including non-empty stable `user_id` and `provider` values plus bounded numeric `expires_at`. The response's `email`, `display_name`, and `org_id` keys are optional profile metadata: they remain bounded strings, but an empty value is valid for the pinned Basic provider and is not used as authentication proof. Only a genuine `401` maps to `identity-unverified` and permits unauthenticated provider discovery. A `500`, redirect, malformed/incompatible payload, missing stable identity, timeout, or other identity failure maps to a distinct fixed failure and remains outside provider discovery and authenticated chat state. Header-time body rejection uses bounded reader cancellation, so a hostile `cancel()` cannot hold the auth operation open.

Hermes logout returns exactly `302 Location: /login`. The client requests that response with manual redirect handling, rejects any other status, missing location, external location, or opaque redirect, and then probes `/api/auth/me` for an otherwise valid response. A `401` proves logout. A still-valid identity returns `logout-failed`; an unavailable or malformed probe returns `logout-unverified`. Network or timeout ambiguity may be resolved by the identity probe, but a response that violates the reviewed redirect contract always fails closed and is never converted to signed out by a later `401`.

`browser-auth-session.ts` coordinates this boundary with the reviewed authentication state model. It verifies the shared stable-identity invariant before provider discovery or authenticated UI, rejects stale async completions by generation, suppresses duplicate password submission, and never copies a username or password into its observable snapshot. Logout and expiry call the supplied local invalidation hook before publishing any later state. During that synchronous hook, nested logout or expiry is ignored, and the guard is cleared even if the hook throws; disposal or newer work also makes the outer lifecycle state stale. The session API emits logout only from an authenticated snapshot with a verified stable identity; optional profile metadata may be empty, while malformed or missing stable fields fail closed. `logout_failed` may retry only with the exact retained identity, while signed-out and generic failure states are no-ops. While `logging_out` or `logout_failed`, retry discovery, expiry, and cancel are no-ops, so generic provider actions cannot abort logout or replace its pending/recovery verification state. Only an ambiguous network or timeout logout performs another `/api/auth/me` reconciliation before any discovery could be considered; an active identity or unresolved probe stays in dedicated logout recovery with only `retry-logout`. Direct `BrowserAuthSession.cancel()` is idempotent after the active operation publishes `signed_out`: a duplicate call neither aborts nor publishes and preserves the reviewed provider and selected-provider retention. The application uses the hook to close the active WebSocket and clear client-side session references.

`BrowserAuthView.svelte` binds the lifecycle to the reviewed authentication presentation. It starts with the identity barrier, then exposes password providers only after unauthenticated provider discovery succeeds. Live username and password values travel through a dedicated transient callback, bypass the credential-free `AuthAction` channel, and are removed from the DOM form immediately after submission. Synthetic fixture controls suppress password-manager discovery with fixture-only markers; live controls omit those suppressors and retain the compatible `username`/`current-password` autocomplete and name semantics. Both modes keep the controls read-only until client hydration completes the deliberate username focus transfer; explicit field names, autocomplete tokens, and element references make the ownership invariant independent of field ordering. Pointer submission keeps the owned form and reset button mounted from immediate pointer-down activation through its compatibility click. `Cancel sign-in` emits a distinct `cancel-sign-in` action, which aborts the active password operation through `BrowserAuthSession.cancel()`; its generation and `AbortSignal` fence reject stale completion, while the reviewed provider and selected-provider retention returns the user to the same password form for a safe retry. Ordinary `Back to providers` remains the selection-clearing action. The view directly clears each input's live value and reset default before the cancelable reset event, then clears again after hostile listeners or observers and before the transient callback or credential-free action can inspect the DOM; the hydrated `onreset` guard plus two bounded microtask phases, one queued-task fence, and one final queued-task phase clear each owned field's live value, reset default, and serialized `value` attribute. The fence lets the finite observer delivery caused by the second clear enqueue its bounded task before the final phase closes that task's writes; neither queued phase starts an unbounded observer fight, and every phase is owned by the current password-clear generation so no stale timer survives a new entry or teardown. On first load with JavaScript disabled, the hydration fence leaves the fields read-only, so the server-rendered form is an inert loading boundary that cannot accept credentials. After hydration with JavaScript active, the keyboard handler intercepts Enter from either field, clears the live values through the existing clear-before-callback/action path, and submits through the local callback. If execution is disabled after hydration, a native click on the reset-type primary button or Enter while that button is focused invokes reset semantics and clears the values; `method="dialog"` only keeps that native form path from navigating or posting. A real Chromium probe disables script execution after hydration and checks only browser-observable request, URL/navigation, storage, and a credential-serialization count: no request, navigation, storage mutation, or credential serialization. Native live input values may remain after script execution stops, so the probe does not require those properties to be cleared and does not claim complete DOM or screenshot redaction. The password-cancel return keeps the same keyed form and Pill instance through the compatibility click, then re-establishes field ownership and username focus; form replacement is reserved for provider-selection returns and actual task changes. The view publishes authenticated content only after the session owns a verified identity, and renders only fixed local error messages and codes. `logging_out` has no retry or cancellation action; `logout_failed` exposes only `Retry sign out` and never falls through to generic sign-in or provider-discovery recovery.

The normal `/` product route now composes this authentication session with the live REST and browser chat workspace. Only `scenario=success`, `scenario=empty`, and `scenario=failure` select the deterministic fixture lane; route selection waits for browser mount so server and client hydration stay identical. Authentication invalidation closes the live workspace before logout or expiry publishes its next state. The full browser-to-Hermes Playwright journey remains required. A visible logout control must first have a matching approved Paper state.

## Credential-safe native browser proof

The disabled-script Chromium lanes are proof fixtures, not live authentication. Each lane generates a one-use synthetic username and password inside the page with `crypto.randomUUID()`. The values never pass through Playwright `fill` arguments, evaluate arguments, request fixtures, URLs, console messages, or test titles. Because Playwright's default failure artifacts can retain action parameters, the credential-bearing UI-preview and live-root groups explicitly set `trace: 'off'`, `screenshot: 'off'`, and `video: 'off'`, and assert those resolved settings at runtime. The page global, input values, defaults, serialized attributes, FormData instrumentation, routes, listeners, CDP session, and storage fixtures are scrubbed or detached in `finally` blocks.

Storage proof seeds a same-key cookie, `localStorage` entry, `sessionStorage` entry, and the reviewed IndexedDB record. It overwrites those same keys and proves that the keyed fingerprint changes, then restores the seed and proves supported keyed equality before the native action. A fresh per-test, non-extractable 32-byte page-local HMAC-SHA-256 key is imported and signing-probed before storage collection. Raw local/session/IndexedDB values stay inside the page-side `page.evaluate` boundary and are HMACed there; the same-key overwrite/restore calibration leaves only supported, untruncated counts, flags, and a non-reversible keyed fingerprint in the test result.

Cookie evidence uses `context.cookies([exact current page URL])`, not an unscoped cookie read. The helper validates the exact current origin plus cookie domain/path applicability and binds cookie name, origin, domain, path, `secure`, `httpOnly`, `sameSite`, and `expires` metadata into the HMAC context. That exact URL scope covers applicable HttpOnly cookies as well as script-visible cookies. Each raw cookie value is consumed transiently, immediately HMACed, and cleared before only its non-reversible digest crosses into the page-side canonical record set. IndexedDB access is restricted to the exact reviewed database, object store, and key; unexpected database names, stores, or metadata fail closed before unrelated records are used.

A `status: 'supported'` snapshot is complete, bounded, and untruncated with counts, metadata, and keyed fingerprint. A `status: 'truncated'` snapshot exposes the bounded record limit and per-store truncation flags, with counts, digest, and fingerprint null. Access, validation, crypto import/probe/sign, canonicalization, or other failures return a `status: 'unsupported'` all-null snapshot; no weak hash is substituted. `storageEvidenceEqual` is true only for two valid supported, untruncated snapshots whose bounded metadata, truncation flags, fingerprint, and exact own data-descriptor flags match at both the top level and nested truncation record; accessors, symbols, inherited/custom-prototype fields, and proxies fail closed. Truncated or unsupported evidence never proves equality. No raw values, URLs, errors, request headers or payloads, credentials, cookie payloads, database records, or browser artifacts are retained or returned. The native action is compared with that calibrated baseline for both click and focused-button Enter activation.

The native proof claims are intentionally bounded. It checks no observed request, no observed navigation or history change, no storage digest mutation, no serialized credential match, and no observed `formdata` event or wrapped `FormData` construction. Those FormData counters describe only activity visible to the page instrumentation; they are not an assertion about browser-internal implementation work that bypasses page JavaScript. The true no-JavaScript lane uses a context/project with `javaScriptEnabled: false` and proves the initially server-rendered loading boundary is inert. The separate CDP lane first hydrates the page with JavaScript enabled, then disables execution in that already-hydrated page; CDP script disabling is not an isolated-world guarantee, so the native action uses precomputed geometry and raw protocol mouse/keyboard input rather than Playwright locator actions. After hydrated script execution is disabled, the native reset-button click and focused-button Enter lane records the verified live, default, and serialized field outcome for the tested Chromium build. Pressing Enter from a live input is covered separately as a fail-closed native lane and records its observed DOM outcome rather than assuming that browser-default behavior retains or clears values. The proof does not claim complete DOM, screenshot, or browser-internal memory redaction beyond these scoped observations.
