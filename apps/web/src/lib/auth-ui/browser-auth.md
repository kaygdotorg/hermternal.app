# Browser authentication boundary

`browser-auth.ts` implements the reviewed browser-cookie operations for W-04:

- `POST /auth/password-login` with the selected password provider;
- `GET /api/auth/me` as the required identity-verification barrier; and
- `POST /auth/logout`, followed by `GET /api/auth/me` to prove the server session is gone.

The implementation uses relative same-origin paths, `credentials: same-origin`, no-store requests, bounded response bodies, fatal UTF-8 decoding, duplicate-key-rejecting JSON, fixed diagnostics, and explicit cancellation. Password login rejects duplicate actions. The password response deadline remains active through bounded body consumption; caller cancellation or timeout cancels the reader before the transient normalized input can remain in an open read. Provider discovery applies the same cancellation rule to streamed and no-body synthetic responses. A same-generation `ProviderDiscoveryError('aborted')` is treated as cancellation, while other provider failure codes remain visible as bounded provider-unavailable state. Logout coalesces duplicate actions and treats the identity probe as the authority only for genuinely ambiguous network or timeout outcomes.

A password exists only in the transient request input and JSON request body. The boundary does not place passwords, cookies, refresh material, provider response details, or identity tokens in storage, URLs, errors, diagnostics, fixtures, or retained output. Hermes owns the protected session cookies. The browser never reads their values.

Password login success is not enough to enable chat. The exact `GET /api/auth/me` response must pass the strict REST identity projection first, including non-empty stable `user_id` and `provider` values plus bounded numeric `expires_at`. The response's `email`, `display_name`, and `org_id` keys are optional profile metadata: they remain bounded strings, but an empty value is valid for the pinned Basic provider and is not used as authentication proof. Only a genuine `401` maps to `identity-unverified` and permits unauthenticated provider discovery. A `500`, redirect, malformed/incompatible payload, missing stable identity, timeout, or other identity failure maps to a distinct fixed failure and remains outside provider discovery and authenticated chat state. Header-time body rejection uses bounded reader cancellation, so a hostile `cancel()` cannot hold the auth operation open.

Hermes logout returns exactly `302 Location: /login`. The client requests that response with manual redirect handling, rejects any other status, missing location, external location, or opaque redirect, and then probes `/api/auth/me` for an otherwise valid response. A `401` proves logout. A still-valid identity returns `logout-failed`; an unavailable or malformed probe returns `logout-unverified`. Network or timeout ambiguity may be resolved by the identity probe, but a response that violates the reviewed redirect contract always fails closed and is never converted to signed out by a later `401`.

`browser-auth-session.ts` keeps `logging_out` and `logout_failed` as internal lifecycle states. It verifies the shared stable-identity invariant before provider discovery or authenticated UI, rejects stale async completions by generation, suppresses duplicate password submission, and never copies a username or password into its observable snapshot. Logout and expiry call the supplied local invalidation hook before publishing any later state. During that synchronous hook, nested logout or expiry is ignored, and the guard is cleared even if the hook throws; disposal or newer work also makes the outer lifecycle state stale. The session API emits logout only from an authenticated snapshot with a verified stable identity; optional profile metadata may be empty, while malformed or missing stable fields fail closed. `logout_failed` may retry only with the exact retained identity, while signed-out and generic failure states are no-ops. While `logging_out` or `logout_failed`, retry discovery, expiry, and cancel are no-ops, so generic provider actions cannot abort logout or replace its pending/recovery verification state. Only an ambiguous network or timeout logout performs another `/api/auth/me` reconciliation before any discovery could be considered; an active identity or unresolved probe stays in dedicated logout recovery with only `retry-logout`.

The approved Paper Authentication surface intentionally does not expose `logging_out` or `logout_failed` as presentation states. `BrowserAuthView.svelte` therefore keeps the authenticated projection mounted during those internal states and only returns to the seven reviewed families after the session proves signed-out. This preserves the lifecycle safety boundary without inventing an unreviewed logout panel or allowing generic sign-in controls to interrupt logout. A visible logout recovery control requires a future Paper state first.

The public mocked/local presentation contract contains seven semantic families: provider selection, password sign-in, OAuth callback, authentication failure, session expired, provider discovery, and interaction/accessibility evidence. The `AuthViewState` leaf values retain the approved password-submitting and discovery retry/empty/malformed/aborted/unavailable presentation records so each Paper board remains directly testable. Interaction, localization, and zoom evidence are CSS/test dimensions rather than new authentication states. Fixture providers render every reviewed capability, including unavailable rows, and use the desktop/mobile copy from the approved Paper boards. The session-expired fixture explicitly models a retained local draft; it never persists credentials or sends a prompt after expiry.

`AuthPreview.svelte` binds the lifecycle to that presentation. Live username and password values travel through a dedicated transient callback, bypass the credential-free `AuthAction` channel, and are removed from the DOM form immediately after submission. Synthetic fixture controls suppress password-manager discovery with fixture-only markers; live controls omit those suppressors and retain the compatible `username`/`current-password` autocomplete and name semantics. Both modes keep the controls read-only until client hydration completes the deliberate username focus transfer. Pointer submission keeps the owned form and reset button mounted through the compatibility click, while the shared pill suppresses duplicate activation. The components use semantic Paper tokens, fixed accessible names/tooltips, 44px effective targets, reduced-motion, reduced-transparency, and forced-colors branches. All provider discovery and fixture behavior remains mocked or same-origin gated; no production provider call, credential storage, live Hermes dependency, or deployment is introduced by the UI preview.

The normal `/` product route composes this authentication session with the live REST and browser chat workspace. Only `scenario=success`, `scenario=empty`, and `scenario=failure` select the deterministic fixture lane; route selection waits for browser mount so server and client hydration stay identical. Authentication invalidation closes the live workspace before logout or expiry publishes its next state. The full browser-to-Hermes Playwright journey remains required. A visible logout control must first have a matching approved Paper state.
