# Browser authentication boundary

`browser-auth.ts` implements the reviewed browser-cookie operations for W-04:

- `POST /auth/password-login` with the selected password provider;
- `GET /api/auth/me` as the required identity-verification barrier; and
- `POST /auth/logout`, followed by `GET /api/auth/me` to prove the server session is gone.

The implementation uses relative same-origin paths, `credentials: same-origin`, no-store requests, bounded response bodies, fatal UTF-8 decoding, duplicate-key-rejecting JSON, fixed diagnostics, and explicit cancellation. Password login rejects duplicate actions. The password response deadline remains active through bounded body consumption; caller cancellation or timeout cancels the reader before the transient normalized input can remain in an open read. Provider discovery applies the same cancellation rule to streamed and no-body synthetic responses. Logout coalesces duplicate actions and treats the identity probe as the authority only for ambiguous transport outcomes.

A password exists only in the transient request input and JSON request body. The boundary does not place passwords, cookies, refresh material, provider response details, or identity tokens in storage, URLs, errors, diagnostics, fixtures, or retained output. Hermes owns the protected session cookies. The browser never reads their values.

Password login success is not enough to enable chat. The exact `GET /api/auth/me` response must pass the existing strict REST identity projection first. Only a genuine `401` maps to `identity-unverified` and permits unauthenticated provider discovery. A `500`, redirect, malformed/incompatible payload, timeout, or other identity failure maps to a distinct fixed failure and remains outside provider discovery and authenticated chat state. Header-time body rejection uses bounded reader cancellation, so a hostile `cancel()` cannot hold the auth operation open.

Hermes logout returns exactly `302 Location: /login`. The client requests that response with manual redirect handling, rejects any other status, missing location, external location, or opaque redirect, and then probes `/api/auth/me` for an otherwise valid response. A `401` proves logout. A still-valid identity returns `logout-failed`; an unavailable or malformed probe returns `logout-unverified`. Network or timeout ambiguity may be resolved by the identity probe, but a response that violates the reviewed redirect contract always fails closed.

`browser-auth-session.ts` coordinates this boundary with the reviewed authentication state model. It verifies identity before provider discovery, rejects stale async completions by generation, suppresses duplicate password submission, and never copies a username or password into its observable snapshot. Logout and expiry call the supplied local invalidation hook before publishing any later state. While `logging_out` or `logout_failed`, retry discovery, expiry, and cancel are no-ops, so generic provider actions cannot abort logout or replace its pending/recovery verification state. An ambiguous logout performs another `/api/auth/me` reconciliation before any discovery could be considered; an active identity or unresolved probe stays in dedicated logout recovery with only `retry-logout`. The application uses the hook to close the active WebSocket and clear client-side session references.

`BrowserAuthView.svelte` binds the lifecycle to the reviewed authentication presentation. It starts with the identity barrier, then exposes password providers only after unauthenticated provider discovery succeeds. Live username and password values travel through a dedicated transient callback, bypass the credential-free `AuthAction` channel, and are removed from the DOM form immediately after submission. The view publishes authenticated content only after the session owns a verified identity, and renders only fixed local error messages and codes. `logging_out` has no retry or cancellation action; `logout_failed` exposes only `Retry sign out` and never falls through to generic sign-in or provider-discovery recovery.

The normal `/` product route now composes this authentication session with the live REST and browser chat workspace. Only `scenario=success`, `scenario=empty`, and `scenario=failure` select the deterministic fixture lane; route selection waits for browser mount so server and client hydration stay identical. Authentication invalidation closes the live workspace before logout or expiry publishes its next state. The full browser-to-Hermes Playwright journey remains required. A visible logout control must first have a matching approved Paper state.
